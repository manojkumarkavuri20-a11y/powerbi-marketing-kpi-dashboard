# Blueprint: Power BI Marketing KPI Dashboard

## Why this repo exists

During my internship at BorderlessHR Inc I got exposure to how digital marketing performance actually gets reported: spend and results scattered across Google Ads, Facebook, and email platforms, with no single view tying CTR, CPC, CAC and ROAS together. This repo is my attempt to build the SQL layer that a marketing or business analyst would write to consolidate that picture, using a synthetic campaign dataset shaped like a real multi-channel export rather than any real employer's or client's data.

The repo is intentionally SQL-first rather than a finished Power BI file. It documents the dashboard I would build on top of these queries, and is honest about the fact that the `.pbix` itself has not been built yet.

## How it's built

The queries run against plain PostgreSQL or MySQL. `data/sample_campaign_data.csv` is the one sample dataset included: 20 synthetic campaigns spanning June to August 2025 across six channels (Paid Search, Social Media, Video, Display, Affiliate, Email), with budget, impressions, clicks, conversions and revenue for each. `docs/findings_report.md` is generated by running `sql/campaign_performance_query.sql`'s logic directly against that CSV, so every figure in the findings report traces back to a real calculation on the sample data, not an invented outcome.

## What the SQL does

`campaign_performance_query.sql` holds five queries. The first aggregates CTR, CPC, CAC, ROAS and conversion rate per campaign, channel and month, the core view everything else builds on. The second rolls that up to a channel comparison summary for an executive view. The third calculates a month-over-month trend with the change in ROAS from the previous month, which is what would power the dashboard's trend line charts. The fourth pulls the top five campaigns by ROAS for card visuals. The fifth breaks channel performance down further by audience segment (cold, warm, retargeting), which is the query that would answer "which audience type actually converts on this channel."

## A schema gap I chose to document rather than hide

The SQL is written against a slightly fuller schema than the sample CSV actually contains: it references `spend`, `leads`, `audience_segment` and `region` columns that represent what a merged ad-platform-plus-CRM warehouse would look like, while the sample CSV is a simpler summary export with `budget_gbp` instead of `spend` and no lead-stage, audience-segment, or region columns at all. `docs/data_dictionary.md` spells out exactly which columns exist where and what would need to change to run the queries against the sample file as-is. I left the SQL written against the fuller schema because the audience-segment and channel-comparison logic is the more interesting analytical work to show, rather than trimming the queries down to only what the smaller sample file supports.

One thing I did fix rather than just document: the first query originally filtered to `channel IN ('Google Ads', 'Facebook', 'Email')`, three values that don't match any of the six channels actually used anywhere else in the file or the sample data. That filter would have silently dropped most campaigns from the results, so I removed it rather than leaving a query that quietly returns the wrong rows.

## What I'd add next

Building the actual `.pbix` file against this SQL layer is the obvious next step, along with generating the additional synthetic fields (leads, audience segment, region) so the full query set can run end to end against one consistent dataset rather than a documented gap between two schemas.
